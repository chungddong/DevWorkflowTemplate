# 개발 규칙

이 문서는 프로젝트를 개발하면서 공통으로 지켜야 할 규칙을 관리하기 위한 문서입니다.

## 1. 작업 시작 전 현재 상태를 확인한다

개발을 시작하기 전에 프로젝트의 현재 상태를 먼저 확인합니다.

확인 대상은 아래 문서를 기준으로 합니다.

- `README.md`
- `docs/DASHBOARD.html`
- `docs/data/project-status.yaml`
- `docs/architecture.md`
- 최근 커밋 기록

AI나 다른 개발자가 작업을 이어받는 경우에는 현재 `phase`, 진행 중인 TODO, 최근 변경사항을 먼저 확인합니다.

## 2. 프로젝트 시작 시 기본 문서와 Git 설정을 준비한다

새 프로젝트를 시작하거나 개발 환경을 처음 구성할 때는 레포지터리 관리를 위해 항상 아래 항목을 준비합니다.

- `README.md`
- `.gitignore`
- `docs/` 폴더

`README.md`는 프로젝트를 처음 보는 개발자나 AI가 빠르게 프로젝트를 파악할 수 있는 진입점으로 작성합니다.

`README.md`에는 최소한 아래 내용을 포함합니다.

- 프로젝트 개요
- 개발 환경
- 빌드 및 실행 방법
- 프로젝트 구조
- 주요 문서 위치
- 현재 개발 상태 또는 다음 작업 안내

`.gitignore`에는 빌드 결과물, IDE 설정 파일, 임시 파일, 외부 의존성 다운로드 폴더처럼 Git에 올리지 않아야 하는 파일과 폴더를 등록합니다.

`docs/` 폴더는 개발 중 생성되는 문서와 프로젝트 상태 데이터를 관리하는 기본 위치로 사용합니다.

## 3. 개발 문서는 한글로 작성한다

개발 중 생성되는 문서는 기본적으로 한글로 작성합니다.

단, 코드, 명령어, 파일명, 라이브러리명, API 이름처럼 원문 표기가 필요한 항목은 영어를 그대로 사용할 수 있습니다.

## 4. 문서와 상태 데이터의 역할을 분리한다

프로젝트 문서는 설명 문서, 상태 데이터, 시각화 결과물로 역할을 분리합니다.

- Markdown 문서: 사람이 읽는 설명과 기록을 관리합니다.
- YAML 데이터: 목표, 마일스톤, TODO, 현재 상태처럼 구조화된 프로젝트 상태를 관리합니다.
- HTML 대시보드: YAML 데이터를 기반으로 자동 생성되는 시각적 결과물로 사용합니다.

HTML 대시보드는 사람이 직접 수정하지 않습니다.

프로젝트 상태를 변경할 때는 `docs/data/project-status.yaml`을 먼저 수정한 뒤 대시보드를 다시 생성합니다.

## 5. 문서 관리 구조를 명확히 한다

모든 프로젝트는 개발을 이어받기 쉽도록 `docs/` 폴더에 문서를 목적별로 정리합니다.

`docs/` 폴더에는 최소한 아래 문서를 준비합니다.

- `docs/README.md`
- `docs/DEVELOPMENT_RULES.md`
- `docs/DASHBOARD.html`
- `docs/data/project-status.yaml`
- `docs/setup.md`
- `docs/architecture.md`
- `docs/notes/`
- `docs/notes/template-feedback.md`

새 문서를 만들면 `docs/README.md`에 링크와 목적을 추가합니다.

루트 `README.md`에는 `docs/`의 주요 문서 위치를 연결해 프로젝트를 처음 보는 사람이 문서에 쉽게 접근할 수 있게 합니다.

## 6. 작업 종료 후 상태 데이터와 대시보드를 갱신한다

기능 구현, 구조 변경, 문서 수정이 끝나면 `docs/data/project-status.yaml`의 `phase`, `milestones`, `todos`를 현재 상태에 맞게 갱신합니다.

상태 데이터를 수정한 뒤 아래 명령으로 대시보드를 다시 생성합니다.

```powershell
python tools\generate_dashboard.py
```

대시보드 생성 결과인 `docs/DASHBOARD.html`은 직접 수정하지 않습니다.

## 7. 결정사항은 개발 메모에 기록한다

구조 선택, 라이브러리 선택, 구현 방향처럼 나중에 다시 확인될 수 있는 결정은 `docs/notes/`에 기록합니다.

결정사항 문서에는 아래 내용을 가능한 한 포함합니다.

- 배경
- 선택지
- 결정 내용
- 결정 이유
- 영향 범위
- 다음에 확인해야 할 내용

정리된 결정사항은 필요에 따라 `docs/architecture.md`, `docs/setup.md`, `docs/data/project-status.yaml`에 반영합니다.

## 8. 파일 구조 변경은 구조 문서에 반영한다

폴더 구조, 주요 모듈, 실행 흐름이 바뀌면 `docs/architecture.md`를 함께 수정합니다.

새로운 주요 디렉터리나 파일이 생기면 역할과 책임을 문서에 남깁니다.

## 9. 외부 의존성 추가 시 환경 문서에 기록한다

새 라이브러리, SDK, 도구, 런타임을 추가하면 설치 방법과 사용 이유를 `README.md` 또는 `docs/setup.md`에 기록합니다.

빌드 명령, 실행 명령, 필요한 환경 변수, OS별 주의사항이 있으면 함께 남깁니다.

## 10. 변경 후 검증 결과를 기록한다

코드 변경 후 가능한 범위에서 빌드, 테스트, 실행 확인을 수행합니다.

검증 결과는 커밋 본문, 작업 문서, 또는 관련 메모에 기록합니다.

검증하지 못한 항목이 있다면 이유를 함께 기록합니다.

## 11. 템플릿 개선 피드백을 기록한다

프로젝트를 진행하면서 다른 프로젝트에도 적용할 수 있는 문서 구조, 개발 규칙, 도구 개선이 생기면 `docs/notes/template-feedback.md`에 기록합니다.

피드백에는 아래 내용을 포함합니다.

- 배경
- 변경 내용
- 변경 전 구조
- 변경 후 구조
- 기대 효과
- 템플릿 저장소 반영 제안

프로젝트 고유 요구사항은 템플릿 피드백에 포함하지 않습니다.

여러 프로젝트에서 반복적으로 유용한 내용만 템플릿 피드백으로 기록합니다.

템플릿 저장소에서는 이 피드백 문서를 참고해 GitHub Copilot 또는 AI와 함께 범용 항목만 반영합니다.

## 12. 커밋은 하나의 의도를 담는다

한 커밋에는 하나의 의도만 담습니다.

문서 구조 변경, 기능 구현, 버그 수정, 리팩터링이 섞이면 가능한 한 커밋을 분리합니다.

큰 변경은 `docs/data/project-status.yaml`의 마일스톤 또는 TODO와 연결합니다.

## 13. 커밋 메시지 규칙

커밋 메시지는 어떤 종류의 변경인지 한눈에 구분할 수 있도록 제목 앞에 약어를 붙입니다.

### 커밋 제목 형식

```text
[약어] 커밋 제목
```

### 커밋 본문 형식

커밋 본문에는 어떤 파일에서 어떤 변경이 있었는지 개조식으로 작성합니다.

```text
[약어] 커밋 제목

- 파일명
  - 변경 내용
  - 변경 내용
- 파일명
  - 변경 내용
```

### 커밋 약어

- `INIT`: 프로젝트 초기 설정
- `FEAT`: 기능 추가
- `FIX`: 버그 수정
- `DOCS`: 문서 작성 또는 수정
- `STYLE`: 코드 포맷팅, UI 스타일, 주석처럼 동작 변경이 없는 수정
- `REFACTOR`: 기능 변경 없이 코드 구조 개선
- `BUILD`: 빌드 설정, 의존성, 프로젝트 설정 변경
- `TEST`: 테스트 추가 또는 수정
- `CHORE`: 기타 유지보수 작업
